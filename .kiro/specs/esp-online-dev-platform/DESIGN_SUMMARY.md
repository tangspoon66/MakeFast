## 关键技术决策

### 1. 前端技术栈
- **React 18 + TypeScript + Vite**: 现代化、类型安全的开发体验
- **Web Serial API**: 浏览器原生硬件通信，无需插件
- **esptool-js**: Web 版本的 ESP32 烧录工具

### 2. 后端技术栈
- **Python + FastAPI**: 高性能异步框架，易于开发和维护
- **Arduino CLI**: 成熟的 ESP32 编译工具链
- **Redis**: 任务队列和缓存（生产环境）

### 3. 架构设计
- **前后端分离**: 前端静态托管，后端独立扩展
- **编译服务分离**: API 层和编译层独立部署，便于水平扩展
- **混合库管理**: 预装常用库 + 按需下载，平衡性能和灵活性

### 4. 安全设计
- **代码沙箱**: Docker 容器隔离编译环境
- **输入验证**: 严格验证代码内容和开发板 ID
- **速率限制**: 防止滥用（10 次/分钟）
- **资源限制**: CPU、内存、磁盘、超时限制

## Property-Based Testing 评估

**结论**: ❌ **不适合使用 PBT**

**原因**:
- 项目主要涉及 **UI 交互**（代码编辑器、按钮、串口选择）
- 项目主要涉及 **硬件通信**（Web Serial API 与 ESP32 设备）
- 项目主要涉及 **外部服务集成**（arduino-cli 工具链、库下载）
- 这些场景不符合 PBT 的适用条件（纯函数、可预测的输入输出关系）

**替代测试策略**:
- ✅ **单元测试**: 测试纯函数逻辑（include 解析、错误解析）
- ✅ **集成测试**: 测试 API 端点和编译流程
- ✅ **E2E 测试**: 测试完整用户流程
- ✅ **Mock 测试**: 模拟硬件和外部服务

## 部署方案

### 方案 1: 单机部署（开发/测试）
- **成本**: ¥250/月
- **规模**: <100 用户
- **配置**: 4核8G + Docker Compose

### 方案 2: 生产部署（推荐）
- **成本**: ¥1960/月
- **规模**: 1000-5000 用户
- **配置**:

## 核心功能实现要点

### 1. 代码编译流程
```
用户代码 → 解析 #include → 确保库可用 → arduino-cli 编译 → 返回固件或错误
```

### 2. 库管理策略
- **预装 20-30 个常用库**（WiFi、PubSubClient、ArduinoJson 等）
- **按需下载**：检测缺失 → 从 Arduino Library Manager 下载 → 缓存
- **超时保护**：60 秒下载超时

### 3. 固件上传流程
```
请求串口 → 用户选择 → 打开连接 → 复位设备 → 上传数据 → 显示进度 → 完成
```

### 4. 错误处理
- **7 类错误**：输入错误、兼容性错误、编译错误、库管理错误、超时错误、上传错误、系统错误
- **统一响应格式**：包含错误类型、友好提示、错误 ID
- **自动重试**：临时性错误自动重试 3 次
- **资源清理**：确保临时文件和连接正确释放
